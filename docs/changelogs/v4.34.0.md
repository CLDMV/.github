# v4.34.0 — 2026-10-31

Minor release that adds a `status: implemented - dev` lifecycle label, fixes the org label sync, which had errored for every repo since v4.33.0, and makes its per-repo failures visible in the job log.

## Added

- **`status: implemented - dev` lifecycle label.** `data/github-labels.json` gains a status between `status: in progress` and `status: implemented` for work that is built and pushed to a `dev` working branch but not yet merged into `next` or `hotfixes`. `mark-implemented-issues` already replaces every other `status:` label when it marks an issue, so an issue carrying the new label moves to `status: implemented` once its PR merges, and a test covers that. ([#405](https://github.com/CLDMV/.github/pull/405))

## Fixed

- **The `release: deps-only` label description fits GitHub's 100-character limit.** The description added in v4.33.0 was longer than the cap GitHub enforces on label descriptions, so creating or updating that label was rejected and the sync reported an error for every repo it processed. `data/github-labels.json` now carries a shorter description ("Release PR that only touches devDependencies, lockfiles and CI config — held, not released") that keeps the meaning and fits the limit. ([#398](https://github.com/CLDMV/.github/pull/398))
- **Per-repo sync errors are printed to the job log.** `sync-org-labels` wrote each repo's errors only to the step summary, so a failing run showed nothing in the log itself and the cause above went unnoticed. Each error is now also written to the log, prefixed with the repo name. ([#398](https://github.com/CLDMV/.github/pull/398))

## Tests

- **A label-length validation test guards the label data.** `data/github-labels.test.mjs` fails when any label name or description in `data/github-labels.json` exceeds GitHub's length limits, so an over-long description is caught by `npm test` instead of surfacing as a sync failure across the org. It is wired into the `test` script. ([#398](https://github.com/CLDMV/.github/pull/398))

## Upgrade notes

- No action for consumers. The new label and the corrected label description reach repos the next time the org label sync runs, and the sync fix is reached through the rolling `@v4` tag once `v4` points at this release.
