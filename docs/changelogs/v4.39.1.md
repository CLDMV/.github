# v4.39.1 — 2026-11-18

Patch release with two fixes: a default branch with no `package.json` at all no longer makes `next` re-bump on every push (finishing the v4.37.1 first-release fix), and sync-release-notes finds release PRs by their commit again when it runs with the bot token.

## Bug Fixes

- **First releases on repos with no `package.json` on the default branch.** v4.37.1 treated a `package.json` with no `version` field as base 0.0.0, but a default branch with no `package.json` still read as an unknown base. That skips the already-bumped check, so every push to `next` bumped again (github-platform went from 0.1.0 to 0.2.0 after its changelog PR merged, and the release PR then asked for a v0.2.0 changelog). A missing file is now base 0.0.0 as well. The release-PR opener's copy of the same lookup now shares the helper. ([#492](https://github.com/CLDMV/.github/pull/492), fixes [#491](https://github.com/CLDMV/.github/issues/491))

- **sync-release-notes and the bot token.** A dry run on llm-translator showed why the commit lookup never matched: with the bot App token, both the commit's PR listing and `GET /pulls/{n}` come back with `merged_at` and `base` but no `merge_commit_sha`, so every release fell back to the title lookup. A merged PR into the default branch that came from listing the release commit is now accepted without `merge_commit_sha`; a PR whose `merge_commit_sha` names a different commit is still rejected. ([#495](https://github.com/CLDMV/.github/pull/495), fixes [#468](https://github.com/CLDMV/.github/issues/468))

## Upgrade notes

- No caller changes. A repo that already re-bumped corrects itself on the next Next Release run: `check-release-commit` sees that the version it expects was bumped earlier but `package.json` has moved past it, and bumps back.
